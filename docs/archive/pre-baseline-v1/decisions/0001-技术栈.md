# 0001：桌面版技术栈

日期：2026-09-22。状态：选定技术方向；工具链组合、导出和性能尚待首次工程验证。用户已确认Windows桌面优先；本次只形成设计，不创建游戏实现或安装开发环境。

## 决定

采用 **Godot .NET＋C#＋独立纯C#模拟核心**。Godot负责窗口、输入、二维绘制、界面、音频和资源导入；模拟负责规则、状态、空间查询、导航和能源分配。模拟可在普通.NET进程中运行，不依赖Godot节点或物理回调。

| 部分 | 选择 | 边界 |
| --- | --- | --- |
| 首发 | Windows x64桌面单机 | 保留Linux/macOS适配边界，移植需各自构建与验证；不承诺浏览器、手机或联机 |
| 引擎 | Godot 4.7.2 stable的.NET版本，作为首次工程候选基线 | 编辑器、Godot.NET.Sdk与导出模板锁定匹配版本，不使用dev/RC版本 |
| 语言与运行时 | C#，.NET 10 LTS SDK；目标框架拟采用net10.0 | 不启用预览语言特性；SDK精确补丁版本在首次编译/导出验证后写入global.json，不能把运行时版本号当SDK版本号 |
| 绘制 | 2D Compatibility起步 | 无高级光照/计算着色器依赖；批量敌人与弹体绘制独立于模拟 |
| 模拟组织 | 连续数据容器＋按能力分组的系统循环 | 暂不引入第三方ECS、依赖注入容器、通用消息总线或原生扩展 |
| 内容 | UTF-8 JSON；System.Text.Json加载为强类型定义 | JSON是规则数据唯一来源；Godot场景/资源不再存第二份伤害、价格等参数 |
| 美术 | SVG原稿，PNG图集/导入纹理；少量程序图形与CanvasItem着色器 | 初始不引入外部资产打包服务；模拟不引用纹理路径 |
| 验证 | xUnit规则测试；纯.NET场景运行器；Godot headless集成检查 | 宏观性能使用导出的Release程序；无界面结果不能替代GPU与画面验证 |
| 工具 | dotnet CLI、Godot CLI、GitHub Actions | 编辑器可用VS Code/Visual Studio/Rider，不作为构建前置；包版本固定并提交锁文件 |

官方归档已列出[4.7.2稳定版](https://godotengine.org/download/archive/4.7.2-stable/)。[Godot C#文档](https://docs.godotengine.org/en/4.7/tutorials/scripting/c_sharp/c_sharp_basics.html)要求.NET版编辑器与独立SDK，支持桌面导出，但Godot 4 C#不能导出Web。该页最低SDK说明仍引用较早引擎版本，因此不能据此声称4.7.2与net10.0组合已经实测。首次工程必须验证编辑器加载、项目引用、headless和Windows Release导出；失败时先核查官方支持矩阵并修订本决策，不能默默降级或更改平台目标。

[.NET支持政策](https://dotnet.microsoft.com/en-us/platform/support/policy/dotnet-core)列出.NET 10为LTS、支持至2028-11-14；.NET 8/9均将在2026-11结束支持，因此新项目不把它们作为长期运行时基线。SDK、目标框架和Godot版本各自记录，升级作为有回归检查的显式变更。

## 为什么这样选

| 方案 | 对本项目的优势 | 需要承担的成本 | 结论 |
| --- | --- | --- | --- |
| Godot＋C# | 二维编辑、界面与导出有现成工具；规则可脱离引擎测试；同一语言覆盖算法与呈现适配 | C#与引擎交互有成本；批量渲染和纯数据模拟边界需要自己设计；Web受限 | 采用，先证明最小交战与规模探针 |
| Unity 6 LTS＋C#，必要时Jobs/Burst | 成熟编辑工具，有官方数据并行与原生编译路径 | Jobs/Burst的数据约束与资源生命周期增加设计成本；Entities工作流需额外学习与维护 | 备选；若实测表明CPU热点难以满足目标，再基于同场景比较 |
| Godot＋GDScript | 与节点、编辑器结合直接，适合小型原型 | 我们选择把高频规则和无引擎测试统一放在C#，不再维护两种玩法语言 | 不作为主要玩法语言 |
| 自建C++/Rust框架 | 可精细控制数据和调度 | 同时承担编辑、UI、资源、平台和调试工具工作 | 当前规模不值得承担这部分工作 |

这些结论是针对本项目维护成本的判断，不是引擎性能排名。[Unity Jobs](https://docs.unity3d.com/6000.0/Documentation/Manual/job-system-overview.html)提供多核调度；[Burst](https://docs.unity3d.com/6000.0/Documentation/Manual/script-compilation-burst.html)针对受限C#代码编译优化，不能将普通托管对象逻辑自动全部加速。我们不因选择Godot就排除数据导向设计，也不以“选了ECS”代替算法与负载测量。

## 性能能力与限制

[Compatibility渲染器](https://docs.godotengine.org/en/stable/tutorials/rendering/renderers.html)适合无需高级渲染功能的2D项目，并覆盖较老硬件。这是初始选择；实际驱动兼容性、线条抗锯齿和大规模绘制需要在目标硬件验证。

[MultiMesh](https://docs.godotengine.org/en/stable/tutorials/performance/using_multimesh.html)可批量绘制实例，但不能逐实例裁剪。我们按外观、材质和空间块分批，避免全地图一个巨型批次；它只降低绘制提交成本，不能加速寻路、碰撞或伤害结算。

[线程安全约束](https://docs.godotengine.org/en/stable/tutorials/performance/thread_safe_apis.html)要求谨慎处理SceneTree和资源访问。本项目的工作线程只处理纯数据，主线程提交Godot资源与场景更新；先单线程建立可复查基线，再按实测热点并行。

Godot支持[headless运行](https://docs.godotengine.org/en/stable/tutorials/export/exporting_for_dedicated_servers.html)，用于引擎适配层的自动检查；多数规则与场景测试直接运行纯.NET核心，无需启动引擎。

## 生效与重新评估

具体模块、数据、时序、性能预算和首次工程门槛见[技术架构](../design/技术架构.md)。架构方向现在生效，版本锁定在工具链探针通过后落地；当前没有已安装工具链、可运行入口或性能成绩。

若用户新增浏览器首发要求，或基准硬件上经过定位与局部优化仍无法满足目标，应重新评估本决策。优先检查算法、数据布局、绘制提交与GC，再考虑局部原生模块或更换引擎；不预先维护两套引擎实现。
